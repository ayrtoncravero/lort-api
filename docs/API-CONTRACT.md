# LORT API Contract

Generated by inspecting the actual source code (`lort-api/src`, `lort-api/data`), the generated Swagger document, and by running live requests against a locally started instance. This document describes the **current, implemented** state only. Nothing here is a proposal or a plan.

Audit date: 2026-08-27.

## Base URL

```
http://localhost:3001/api
```

Global prefix `api` is set in `src/main.ts` via `app.setGlobalPrefix('api')`. Port comes from `PORT` env var (default `3000`; the audit ran the instance on `3001`).

## Version

`0.1.0` — declared in the Swagger `DocumentBuilder` config (`src/main.ts`). This is Swagger-document metadata only; there is no `/api/v1` style versioning and no version header.

## Authentication

**NOT IMPLEMENTED.** No guards, no API keys, no auth headers checked anywhere in `src/`. Every endpoint is open.

## Common behavior

- All responses are JSON.
- CORS is enabled, origin controlled by `CORS_ORIGIN` env var (default `*`). Configured in `src/config/configuration.ts` / `src/main.ts`.
- Global `ValidationPipe` (`src/main.ts`) with:
  - `whitelist: true` — strips properties not declared in the DTO... but combined with the next option, unknown properties actually cause a **400**, not silent stripping.
  - `forbidNonWhitelisted: true` — confirmed live: `GET /api/characters?foo=bar` → `400 {"message":["property foo should not exist"]}`.
  - `transform: true` — query strings are cast to declared types (e.g. `page`/`limit` become numbers).
- Every controller across all 4 domains is deliberately thin: it only calls its service and returns the result. No business logic in controllers (verified by reading every controller file).
- There is no global response-wrapping interceptor; the paginated envelope described below is built manually per-service via a shared `paginate()` helper (`src/common/utils/paginate.ts`).

## Pagination

Implemented via `PaginationQueryDto` (`src/common/dto/pagination-query.dto.ts`), extended per-domain, and applied via the shared `paginate<T>()` helper (`src/common/utils/paginate.ts`).

| Param | Type | Default | Constraints |
|---|---|---|---|
| `page` | integer | `1` | `Min(1)` — no upper bound |
| `limit` | integer | `20` | `Min(1)`, `Max(100)` |

Envelope returned by every **collection** endpoint (`GET` without `:id`):

```json
{
  "data": [ /* array of resource objects */ ],
  "page": 1,
  "limit": 20,
  "total": 19
}
```

`total` is the count of the **filtered** set, before slicing — confirmed identical shape on `characters`, `movies`, `books`, `quotes` (each has its own `Paginated*ResponseDto`, structurally identical).

Verified live behavior:

| Case | Result |
|---|---|
| `page=0` | `400`, `"page must not be less than 1"` |
| `limit=0` | `400`, `"limit must not be less than 1"` |
| `limit=101` | `400`, `"limit must not be greater than 100"` |
| `limit=abc` (non-numeric) | `400`, multiple validation messages (not-an-integer + min/max) |
| `page=99` (beyond available data) | `200`, `{"data":[],"page":99,"limit":20,"total":19}` — **not** a 404, just an empty page |
| no `page`/`limit` given | defaults `page=1`, `limit=20` apply |

Pagination is in-memory (`Array.slice`) over the full JSON file loaded on every request — there is no server-side index or cursor.

## Errors

Global `HttpExceptionFilter` (`src/common/filters/http-exception.filter.ts`), `@Catch()` on everything. Actual shape (verified live, matches code):

```json
{
  "statusCode": 404,
  "message": "Character with id \"does-not-exist\" not found",
  "error": "Not Found",
  "path": "/api/characters/does-not-exist",
  "timestamp": "2026-08-28T01:41:43.059Z"
}
```

Note this has **two extra fields** (`path`, `timestamp`) beyond the minimal `{statusCode, message, error}` shape referenced in older discussion — the filter always adds them.

- **400** — thrown by `ValidationPipe` for bad query/path DTOs. `message` is an **array of strings** in this case (class-validator format), not a single string.
- **404** — thrown explicitly by each service's `findById()` via `NotFoundException` when the repository returns `null`. Message format: `"<Entity> with id \"<id>\" not found"`.
- **500** — code-verified only (not triggered live, to avoid touching data): `JsonDataLoader.load()` (`src/infrastructure/json/json-data-loader.ts`) throws `InternalServerErrorException` if the JSON file is missing or fails to parse.

## Health

```
GET /api/health
```

- No query/path params, no DTO.
- Controller (`HealthController`) has **no service layer** — it's the only domain implemented as controller-only, since there's no business logic to isolate.
- Response: `200 {"status":"ok"}` (verified live).

## Characters

```
GET /api/characters
GET /api/characters/:id
```

### Entity fields (`Character`, `src/modules/characters/domain/character.entity.ts`)

All fields are `string`, none optional (unset values are stored as `""`, not omitted or `null`):

`id, name, race, gender, birth, death, hair, height, realm, spouse, wikiUrl`

### `GET /api/characters`

- Query DTO: `FindCharactersQueryDto` extends `PaginationQueryDto` + `name?`, `race?`, `gender?` (all optional strings).
- Filter semantics (in `CharacterService.findAll`, in-memory): `name` = case-insensitive **substring** match; `race` and `gender` = case-insensitive **exact** match.
- Response: `PaginatedCharactersResponseDto` → `{data: Character[], page, limit, total}`.
- Verified live: `?race=Hobbit` → 6 matches; `?name=gan` → 1 match (`Gandalf`); default call → `total: 19`.

### `GET /api/characters/:id`

- Path DTO: `FindCharacterByIdDto` (`id: string`, `@IsNotEmpty`).
- 200 → full `Character` object, no envelope.
- Unknown id → 404 (see Errors section).

## Books

```
GET /api/books
GET /api/books/:id
```

### Entity fields (`Book`)

`id: string, name: string` — the smallest entity in the API, only two fields.

### `GET /api/books`

- Query DTO: `FindBooksQueryDto` extends pagination + `name?` (substring, case-insensitive).
- Response: `{data: Book[], page, limit, total}`.

### `GET /api/books/:id`

- 200 → `Book`. 404 on unknown id.

**Inconsistency found**: `BooksModule` does not `export` its `BOOK_REPOSITORY` token (unlike `CharactersModule` and `MoviesModule`, which both export theirs). Currently harmless — nothing imports `BooksModule`'s repository — but it means Books cannot be cross-referenced from another domain (e.g. a future "which book does this character first appear in" feature) without that change. See Findings.

## Quotes

```
GET /api/quotes
GET /api/quotes/:id
```

This is the only domain whose service coordinates **three** repositories: `QuoteRepository`, `CharacterRepository`, `MovieRepository` (all injected into `QuoteService`, `src/modules/quotes/application/services/quote.service.ts`). `QuotesModule` imports `CharactersModule` and `MoviesModule` to get access to those tokens.

### Raw stored entity (`Quote`, data layer only — never returned as-is)

`id: string, dialog: string, movieId: string, characterId: string`

### What the API actually returns (`QuoteWithRelations` / `QuoteResponseDto`)

```ts
{
  id: string;
  dialog: string;
  character: { id: string; name: string } | null;
  movie: { id: string; name: string } | null;
}
```

Confirmed by both code and a live request. `character` and `movie` are **summary objects** (`id` + `name` only) — not the full `Character`/`Movie` entities, and not raw id strings either. `movieId`/`characterId` are **not** present in the response at all.

If a quote references a `characterId`/`movieId` that doesn't exist in the corresponding JSON, the service resolves that relation to `null` rather than erroring (verified in code: `character ? {...} : null`; covered by a unit test).

### `GET /api/quotes`

- Query DTO: `FindQuotesQueryDto` extends pagination + `movieId?`, `characterId?` (both optional strings, **exact match** on the raw id — not substring, not case-insensitive).
- Verified live: `?movieId=the-fellowship-of-the-ring` → 4 matches. `?characterId=gandalf` → 2 matches, both correctly enriched with `character`/`movie`.
- Response: `{data: QuoteWithRelations[], page, limit, total}`.

### `GET /api/quotes/:id`

- 200 → single enriched `QuoteWithRelations`. 404 on unknown id.

### `/random`

**NOT IMPLEMENTED.** There is no `GET /api/quotes/random` route. A request to that exact path is captured by the generic `GET /api/quotes/:id` route, treated as `id = "random"`, and returns a normal 404 (`"Quote with id \"random\" not found"`) — confirmed live. If a "random quote" feature is wanted, it must be added explicitly and placed **before** the `:id` route in the controller (route-ordering concern), since Nest matches routes in declaration order.

## Resources not implemented

- **Places** — no module, no controller, no data file. No code exists for this domain at all.
- **Races** — same: not a separate resource. Race is only a *field* on `Character` (free-text string, e.g. `"Hobbit"`, `"Elf"`, `"Maia"`), not its own entity with its own endpoint.
- **`/quotes/random`** — see above.
- Sorting (`sort`/`order` query params) — not implemented on any endpoint.
- Any write operations (`POST`/`PUT`/`PATCH`/`DELETE`) — the API is 100% read-only; only `GET` routes exist anywhere.
- Any relation embedding beyond quotes (e.g. `GET /api/characters/:id` does not include that character's quotes or movies).

**OPEN DECISION**: full dataset ingestion, `places`/`races` dataset & licensing, database backend, deploy strategy — none of these are decided anywhere in code or config; they remain open per project history.

## Findings

Issues observed during the audit. Not fixed — documentation only, per task scope.

1. **`BooksModule` doesn't export `BOOK_REPOSITORY`**, unlike `CharactersModule`/`MoviesModule`. No current functional impact, but inconsistent with the pattern the other two modules establish, and would block a future cross-domain read of books (the way `quotes` reads `characters`/`movies` today).
2. **`/quotes/random` does not exist** despite being a common convention in comparable APIs (e.g. The One API, which this project's schema is modeled on). Currently silently falls through to `:id` and returns a plain 404 instead of a more meaningful error — worth being aware of if a frontend is built assuming it exists.
3. **Character string fields use `""` instead of `null`/omission** for unknown values (e.g. `height`, `hair` are often empty strings). A frontend expecting to distinguish "field is empty string" from "field is unknown" cannot do so from this contract.
4. **`page` has no upper bound.** `page=999999` returns `200` with an empty `data` array rather than a `400` or `404`. Consistent behavior, just worth documenting explicitly since it differs from how `limit` is bounded.
5. **`HealthController` has no service.** Deliberate (no business logic to isolate) but it's the only domain that deviates from the strict 3-layer pattern used everywhere else — worth a one-line note if new contributors are confused by the asymmetry.
6. **Error `message` field type is inconsistent between error kinds**: a single string for `NotFoundException` (404), but an **array of strings** for `ValidationPipe` failures (400). A frontend parsing `message` needs to handle both shapes.
